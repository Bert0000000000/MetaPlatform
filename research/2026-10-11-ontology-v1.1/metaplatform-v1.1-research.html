MetaPlatform 1.1：Ontology 开源平台深度调研

调研日期：2026-10-11（Asia/Shanghai） · 20 个仓库 · GitHub API 实时元数据 + 许可证原文 + 固定提交源码。 本地基线：feat/ont-migration-plan / 2c13952c。结论是产品设计与源码审计，不是部署、兼容性或整个平台验收报告。

1. 一句话判断

保留 MetaPlatform 现有本体内核、身份与编排，1.1 以“真实数据 → 业务对象 → 可运行应用 → 外部 Agent → 可恢复结果”的完整链路补差。优先借鉴 OpenMetadata 的数据体验、Appsmith/NocoBase 的应用体验和 WebProtégé 的本体编辑方式，复用已有标准 MCP 端点接入 dsh 与 WorkBuddy。

调研对象分为六类：专业本体/语义工具 6 个、图存储 3 个、元数据平台 2 个、应用平台 4 个、Agent/MCP 基础 3 个、图检索/记忆 2 个。高 star 的数据目录、低代码与 Agent 项目能补足相关体验，但不等同于一个完整的业务 Ontology 平台。

产品 1.1 与仓库既有 v3.x 架构版本分开。研究不把历史 GA 文档当作当前全部功能稳定的证据，不改现有 Accepted 或交付看板。

3.3 DataHub：强备选，元数据不是业务数据

固定提交：1634c4f8。读取了 datahub-web-react/package.json、Python ingestion api/source.py、emitter/rest_emitter.py 以及 IngestionSourceBuilder.tsx。接入向导使用多步表单上下文并保护未保存编辑，采集与元数据投递有单独层次。

多步接入组件与Python 采集抽象可以补充 OpenMetadata 对标。DataHub 内部的 MCP 还可能指 MetadataChangeProposal，不能把该缩写自动当作 Model Context Protocol。选择它时仍需验证实际 Agent 接口、运行成本与权限映射。

3.4 专业本体工具与 Agent 记忆

WebProtégé star 只有 805，但本轮读到 ChangeManager.java 的项目锁、RevisionManager、权限与变更处理，及项目共享设置管理。这些比高 star 的通用图数据库更直接服务本体编辑体验。源码快照。不建议把老 Java/GWT UI 搬入 React；借鉴草稿、改动说明、影响与共享权限。

Ontop 面向关系数据库上的虚拟 RDF 查询，Jena 面向 RDF/SPARQL/SHACL；本轮确认了 Jena ShaclValidator 的 conforms 与完整验证报告接口。它们是标准语义互操作参考，不提供现成的业务应用发布与 Action 执行产品。

Graphiti edges.py 和 graphiti.py 提供关系、分组与时态属性，是 Agent 记忆候选；分组字段不自动等于 MetaPlatform 的租户隔离。1.1 不把推断的时态记忆作为已批准业务事实，不替换现有 LightRAG 和本体权威层。

5. dsh 与 WorkBuddy：两种产品方向与可验证接入

1.1 做“外部 Agent 使用 MetaPlatform”；“MetaPlatform 托管外部 Agent”需要单独设计官方生命周期/API，不从 MCP 支持自动推导。

项目 当前已证实 采用路径 验收边界
dsh 固定官方源码支持 stdio 与 streamable-http、自定义 headers、超时和重连；master package 为 alpha 原生 MCP client + Cordis 配置指向 /api/v1/mcp/protocol/mcp；固定目标发行版本 配置导入、真实发现/查询、身份/租户、断线、撤销与写操作确认
WorkBuddy 开放平台连接器文档明确支持 HTTPS streamableHttp、headers 与 stdio；凭据使用 ${VAR_NAME} 引用；不同插件类型有各自格式 优先导出连接器 mcp.json 的原生 HTTP 配置访问既有平台协议端点；本地 stdio 桥按真客户端需要评估 用户安装版本、实际导入/发现/查询、授权续期与插件打包仍需真客户端验收

dsh 传输实现、官方使用说明、WorkBuddy MCP 文档、WorkBuddy 插件文档。本轮 WorkBuddy 原文已直接获取 HTTP 200 并缓存；浏览检索器打开失败不代表官方站没有内容。执行前补充核实 WorkBuddy 开放平台连接器：远程 type 为 streamableHttp，headers/env 使用变量引用，Token 连接器需声明对应最低版本；此格式与企业版 CLI 或 Expert 插件的 type:http 不混用。

工具沿用实际 ont_list_classes / ont_inspect_class / ont_object_query 等名称，默认只读；写入复用现有 ont_preview_proposal / ont_confirm_proposal / ont_execute_proposal。后端验证权限、批准主体、租户与幂等，模型提示词不能代替执行检查。短期复用已有可撤销凭据，后续 HTTP OAuth 完整发现、PKCE 与续期按协议规范及目标客户端能力逐项验收。

标准 MCP HTTP 路径已存在；1.1 不以新增独立 FastMCP 为前置条件。官方 Python SDK 内置的 FastMCP 与 PrefectHQ 的独立包名称相似，升级必须根据实际 API 和协议版本验证。

7. 官网具体设计与入口

官网沿用现有静态页面而做内容和部署接线更新，统一为 MetaPlatform：产品主张、数据 → 本体 → 应用 → Agent 链路、实际能力、订单场景、1.1 规划、常见问题。清除未核实的 demo/邮箱/客户/测试数/GA 口径，开发中的能力明确标注规划。

1. 版本目标与验收主线

让业务人员能够完成“理解平台 → 登录工作区 → 接入数据 → 建立对象与关系 → 校验和发布 → 从模板生成应用 → 在应用中执行经确认的业务动作 → 查看结果、审计与恢复”，让 dsh、WorkBuddy 能在明确权限内消费同一组平台能力。

数据平台管理技术资产、连接与运行；本体平台管理业务语义、对象与动作；应用中心管理业务界面与应用发布；MCP 服务中心管理外部能力与客户端接入。保留现有八域导航，以任务向导和跨域深链串联，先解决实际操作断点。

7. dsh / WorkBuddy 与插件接入

方向一是外部 Agent 使用 MetaPlatform 工具/业务上下文，纳入 1.1。方向二是 MetaPlatform 托管并调度外部 Agent 执行任务，需要其官方调用与生命周期契约，列为后续方案；MCP 不能自动替代 Agent 运行协议。

MCP 能力面沿用现有服务，默认提供只读发现、Schema、对象查询、数据质量/血缘摘要与应用信息。写操作复用 Proposal 的预览、确认和执行链路；授权界面必须显示动作、目标、字段变更与批准期限。Agent 返回需要确认的 Proposal 深链，由已认证人完成确认。工具名、输入/输出 schema 与版本兼容是稳定契约。

当前 ont_confirm_proposal、ont_execute_proposal 等工具已经存在，不能仅凭模型侧提示词保证安全；新增客户端的工具可见性、可调用性与批准主体必须由后端校验。已有 Keycloak/API Key 能力复用，必要的 capability scope 是增量，不另建用户库。HTTP 标准 OAuth 完整发现与 PKCE 支持按客户端真实能力验收，不能把“能接受 Bearer”称为完整 MCP OAuth。

MP11-AGENT-04 P1 连接诊断、撤销、重连与审计深链 区分协议/权限/连接/工具错误；凭据撤销立即有效；超时不自动重复有副作用动作；记录 user/agent/tenant/trace/run
MP11-PLUGIN-01 P1 插件清单、依赖、能力和更新可视化 复用现有 marketplace；展示平台/协议兼容范围、所需权限、健康探测、停用影响、版本与许可证；禁止任意 server 端 npm 自动执行

既有 mcp.server.fastmcp 属于官方 Python SDK；独立 PrefectHQ/FastMCP 是另一套发行与 API，star 数不能作为替换现有协议层的理由。1.1 默认不迁移框架。

完整验收场景：

  1. 官网 → 登录 → 工作区 → PG/CSV 接入 → 字段映射 → 预检 → 发布 → 应用 → 人工批准 → 执行回执，重新登录与重启后仍可追踪。
  2. 错密码、断网、缺权限、重复主键、无效时间列、字段删除、同步中断与重复重试，每个场景都得到可恢复结果。
  3. 1.1.0 的 MCP 协议验证查询同一对象；另一个租户读不到；只读身份无法确认或执行；批准过期不能执行；相同幂等键最多一次副作用。dsh 与 WorkBuddy 真客户端复验纳入 1.1.1。
  4. 空运行树/无效短链/无权应用可解释地失败；任何正式失败不能静默变成演示成功。
  5. 新建测试库与从前一版本升级的测试库都通过；使用临时数据库和独立预览端口，不替换用户正在使用的服务。
