# 最新逆向本体业务审阅

审阅时间：2026-10-10。来源 `d09dfb41-ea94-4b3f-84d2-eab16d6a9b56`，修订 14，发布状态 succeeded，26 个类、33 个关系。本次只读取候选与原生 API，未修改或重新发布本体。来源快照：本地 `.cache/modeling-phase1/latest-business-review.json`。

结论：可以作为 POC 本体骨架；结构发布成功，但业务正确性尚未完成验收。

## 方向合理且已有证据的部分

- 区分物料、供应商、仓库等主数据，采购/到货/入库等单据，以及单据明细。
- 产成品、半成品、材料作为物料的直接子类。原生 API 确认三者 parent_class 指向 material1，并共享其 material_code 主键；这是两层继承，没有为设备空表凭空生成多级分类。
- 将含用量和版本的 BOM 行独立建类，分别关联父项、子项物料，避免丢失关系上的业务属性。
- 采购订单明细区分采购订单号与行号，声明组合身份；这是合理候选规则，长期业务唯一性仍需业务口径确认。

## 明确需要修正的问题

1. **关系基数没有正确表达。** 原生 link-types API 实际返回本次 33 条关系全部为 N:N；publication.py 当前统一写入该值。明细指向其所属单据通常应是 N:1；BOM 行指向父物料或子物料通常也应是 N:1。具体可选性、例外和业务范围需明确。统一放宽基数允许了结构合法但业务错误的关系，是发布适配器的实现缺口。
2. **复合身份的关联漏条件。** purchase_order_line 的原生主键为 purchase_order_id + purchase_line_id，但 rel_shipment_purchase_line 只用 purchase_line_id 匹配。不同订单出现相同行号时会误关联；发运类目前没有 purchase_order_id，不能在没有来源或业务依据时自行填充，需要补充订单上下文或确认一个真正全局唯一的明细标识。当前发运表为空，尚未证明已经发生实例串联，但模型存在歧义。

## 仍需核实的业务规则

- 13/26 个类没有业务 identity，原生以 source-record 技术主键保留。可以发布结构，但这些身份仍未完成业务确认。空表、空值或重复值不能单独证明业务概念本来没有身份；例如设备编码、计划编号、运行批次和结果行粒度应分别定义。MRP 运行标识也不能未经确认就作为每条物料需求结果的唯一标识。
- 工艺路线工序以路线编码 + 工序编码为身份，数据报告存在 16 个同身份标准工时冲突。尚不能断定是数据错误还是漏了版本、适用物料或其他粒度，应核对源记录和业务规则后判断，不能机械追加工时或行号作为主键。
- rel_routing_material 把“路线描述”当物料编码关联。值匹配是证据之一，但不能独立证明业务语义。需要确认该列是错误命名的物料编码，还是描述文本恰好与编码相同。
- 到货单、入库单存在重复编号，入库明细的主单/明细编号疑似互换。关系概念合理，但相应字段语义和编号作用域未完成确认。
- 当前没有到货明细/入库明细到采购订单明细的明确关系，也没有工序的下道工序关系或生产任务到工艺路线工序的关系。相关属性部分存在，但不足以形成完整的追溯链。须先确认字段含义及复合键上下文；不能从字段名直接自动连线。
- 半成品与材料类有定义但没有对应来源映射。这个问题不推翻子类定义本身；后续接入时需要正确的分类映射，防止相同物料产生相互独立的父类、子类对象。
- material1、warehouse1、inventory-balance1、bom-line1、equipment11 与既有类型并存。独立 POC 可保留隔离副本；若成为平台统一业务本体，需要核对语义后选择复用/扩展及迁移，不应靠后缀长期维持多个同义概念。

## 建议的修正顺序

先在候选层修正并审核关系基数和复合键关联，再核定工序、MRP、库存及单据的粒度/业务身份，补齐经确认的业务追溯关系，最后处理与既有类型的复用边界及分类映射。已发布定义的调整沿用平台版本/迁移流程，不直接覆盖，也不要求先导入全部实例。

验收应区分：结构合法、业务语义已确认、数据可接入。前者已通过；后两者不能由发布状态推断。
