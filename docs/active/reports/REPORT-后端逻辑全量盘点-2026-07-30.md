# Mate Platform 后端逻辑全量盘点报告

> 审计日期：2026-07-30  
> 审计对象：现行 Python 后端、网关/认证、基础设施配置、OpenAPI、测试；`legacy/` 与 `docs/legacy/` 仅作为迁移背景，不计入当前实现。  
> 结论口径：**接口路由存在不等于业务实现完成**。本报告要求形成“PRD → 契约 → 路由 → 业务规则 → 数据/外部引擎 → 安全/租户 → 测试”的证据链。

## 1. 执行摘要

### 1.1 总体结论

当前后端更接近一套“**W1–W5 技术验证骨架 + 部分真实适配器 + 大量联调用 mock/fallback**”，不能认定为“所有 PRD 后端逻辑已实现”。

- 现行代码包含 **10 个 packages + 2 个 deployment services**；静态识别约 **134 条装饰器路由**。
- 顶层 PRD/API Contract 覆盖 IAM、APPHUB、WFE、COPILOT、Dashboard、DW、KB、EA、MCP、ONT、RAG、LLMGW、A2A 及 Data Track。扫描全部现行 PRD 得到 795 个去重路径引用（包含版本重复、示例和别名，不能直接作为端点基数），但可以明确证明业务域远多于当前后端路由覆盖。
- `docs/swagger/IMPLEMENTATION-STATUS.md` 所谓“11/11 服务、path 100%”只验证了已有服务契约中的 path 是否有装饰器路由，**未验证全部 PRD，也未验证路由内部是否为 mock、固定返回或内存存储**。
- 本轮未发现任何模块可按 GA 标准评为“完整实现”。IAM 的管理 CRUD、AuthService 的 Keycloak token 校验、消息发布、部分 LLM provider、部分 RAG/Neo4j/Milvus 适配器具有真实代码，但都存在关键边界、安全、持久化、集成或测试门禁缺口。
- v3.1 GA 硬前置 `mate-tech-data` **完全缺失**；Data/ETL/Scheduler/Metrics 接口未实现。
- 架构强制项 Hexagonal/DDD/CQRS/Outbox/Saga/ACL/Nacos/多租户隔离没有形成全仓一致实现；Outbox、Saga、Drools ACL、Nacos 客户端基本未见生产代码。
- 测试虽然 `246 passed`，但默认 pytest 不运行 `tests/integration/`，未开启覆盖率；集成目录存在大量“常量等于常量”的自证测试。Ruff 627 errors、Pyright 701 errors，未达到项目声明的质量门禁。

### 2.2 状态定义

- **已实现**：核心主流程、关键异常、持久化/外部集成、安全租户边界均有代码，且存在有效测试或运行证据。
- **部分实现**：有路由/核心代码，但存在 mock、内存替代、静默 fallback、关键分支/集成/权限/持久化缺口。
- **未实现**：无对应能力，或仅固定返回、占位、全零数据、`NotImplemented`。
- **无法确认**：静态证据不足且运行依赖不可用；本报告不会把“无法确认”当成完成。

## 3. 架构与技术选型符合度

### 3.1 符合项

- Python 3.12、FastAPI、Pydantic v2、SQLAlchemy/SQLModel、httpx、LangGraph、aiokafka、Redis、Neo4j、Milvus 等依赖方向总体与定稿一致。
- AuthService 使用 Keycloak JWKS 和 RS256 系列算法验证 access token，符合“Keycloak 作为 IAM/SSO 外部引擎”的主方向。
- LLM provider 均以 httpx 封装；RAG 和 Agent 也存在独立客户端类，具备 ACL 雏形。
- MSG 有 Kafka producer 和 Redis SET NX 幂等；OBS 有 OTel/Prometheus 基础代码。

### 3.2 不符合或未落地项

| 架构要求 | 当前证据 | 结论 |
|---|---|---|
| 四层 Hexagonal：domain/application/infrastructure/api | 多数包直接由 API 调全局单例/具体 client；目录结构不一致 | 未形成全仓约束 |
| DDD Bounded Context | IAM 有 domain 模型；RAG/Agent/ONT 多为功能脚本与全局 store | 部分 |
| CQRS | 未见明确 command/query handler 与读模型投影 | 未实现为架构模式 |
| Event-Driven + Transactional Outbox | 全生产代码搜索未见 outbox 实现 | 未实现 |
| Saga choreography | 未见 saga 状态、补偿或事件编排实现 | 未实现 |
| Keycloak/Flowable/Drools ACL Client 集 | Keycloak 在 AuthService；Flowable 仅 Agent 且可静默内存回退；Drools client 未见 | 部分/缺失 |
| Nacos 服务发现和配置 | 服务地址大多静态 env/default URL；未见 Nacos client | 未实现 |
| Circuit breaker/bulkhead/retry | LLMGW 有独立 retry helper，但未证明接入主要 API；其他外调多裸 httpx 或吞异常 | 部分 |
| PostgreSQL 多 schema | IAM 默认 SQLite；部分模块内存/JSON | 不符合生产基线 |
| 多租户隔离 | IAM SQL 查询较多带 tenant 条件；RAG/Agent/ONT/MCP 数据模型和全局 store 多数未强制 tenant | 严重不完整 |
| 统一错误模型 | mate-common 有异常类，但各 API 多返回裸 `detail` 或不同 shape | 未统一 |

## 4. 横切模块详细审计

### 4.1 API Gateway

**已实现：**

- `services/api-gateway/.../main.py:23-33` 定义上游服务表；`67-70` 复用 AsyncClient；`157` 有 catch-all 代理。
- Redis 可用时按租户/路径做限流；`readyz` 会探测上游。

**缺口：**

1. 路由表仅显式覆盖 rag/agent/llm/kb/ont/mcp/admin/iam/obs，缺少 msg、dashboard、data、apphub、wfe、copilot、dw、ea、a2a 等 PRD 域。
2. Redis 连接失败后 `app.state.redis=None`，限流直接失效，属于 fail-open；没有本地保护或明确降级告警门禁。
3. 租户身份依赖请求头/上游透传，网关自身未展示对 JWT 签名和 header spoofing 的强绑定。
4. 服务注册是模块级静态字典，没有 Nacos discovery/config。
5. 规范中的 tracing、统一错误 envelope、CORS、安全头、审计等中间件链未形成完整实现。

**评级：部分实现。**

### 4.2 AuthService

**已实现：**

- `auth-service/main.py:52-65` 获取并构建 Keycloak JWKS；`214-276` 按 kid、issuer、audience 验证 token，并检查 Redis blacklist。
- login/refresh 走 Keycloak token endpoint，userinfo 走 OIDC endpoint。

**缺口：**

1. `_jwks_cache` 一旦非空即永久返回，`JWKS_REFRESH_SEC` 没有真正驱动进程内刷新；Keycloak key rotation 可能导致新 token 不可用。
2. Redis 缓存内容并没有从缓存重建 public keys，命中 Redis 后仍重新请求 Keycloak。
3. Redis 不可用时 blacklist 检查失效；logout 又只将未验证 token 的 jti 放入 Redis，未调用 Keycloak end-session/revoke。
4. `/healthz` 永远返回 ok；`readyz` 只报告布尔状态但 HTTP 状态语义未体现依赖不可用。
5. Password grant 对浏览器/公共客户端是否符合 Keycloak 安全策略需进一步产品确认。

**评级：部分实现。**

### 4.3 mate-common

常量、统一 DTO mixin 和异常基类存在，但没有被所有服务一致使用；技术栈所述基础设施 facade、统一租户上下文、统一 trace/error middleware 没有在 common 形成可复用实现。**评级：部分实现。**

## 5. IAM 与 Dashboard

### 5.1 真实实现部分

- 用户、组织、岗位、角色、权限、审计、系统配置使用 SQLModel/SQLAlchemy，并在主要查询中加入 `tenant_id` 条件。
- 有用户状态、密码重置、导入导出、角色权限关联、组织调动等较完整 CRUD。
- 审计记录写入数据库；配置和日志查询有分页/筛选。

### 5.2 关键缺陷

1. **身份源冲突。** 架构指定 Keycloak 拥有 User/Realm/Role，但 `mate-tech-iam/api/auth.py` 自行查本地 User、校验密码并签发 HS256 token，形成第二套身份真相源。文件注释也承认 production 应切换 Keycloak。
2. **授权 Header 可伪造。** `services/deps.py:62-119` 即使没有有效 token 也会产生 anonymous/default tenant；`x-mate-roles` 可直接追加管理员角色，没有基于环境禁用。若服务可被绕过网关直连，攻击者可自赋 `PLATFORM_ADMIN`。
3. **默认密钥不安全。** 默认 `mate-dev-secret-do-not-use-in-prod`；测试运行也出现 HMAC key 长度不足警告。
4. **Dashboard 是显式 mock。** `dashboard.py:1-7` 明确写“Self-contained mock store”；通知、session、API key、todo、worker、deliverable、anomaly、rule、search 等均为模块级列表。
5. **审批未接 Flowable。** todo action 只修改 `_TODOS`；没有任务 claim/complete、变量校验、并发控制。
6. **AIOps 是固定文本。** RCA、remediation、日志、指标为构造数据；`AUTO` 仅返回 `executed=True`，没有实际执行动作。
7. **启动自动 create_all + seed。** 缺少 Alembic/迁移版本治理；默认 SQLite 不符合 PostgreSQL 多 schema 基线。
8. Portal alias middleware 复杂且存在可疑正则/缩进，长期应由明确兼容路由或网关重写替代。

### 5.3 PRD 结论

- 后台管理的基础 CRUD：**部分实现，完成度相对最高**。
- SSO provider 管理：接口固定返回空，**未实现**。
- Dashboard 工作台、通知、待办、数字员工、产物、异常、全局搜索：**仅联调 mock，不算业务实现**。
- Keycloak 企业 IAM/SSO 与本地管理模型同步：**未形成闭环**。

## 6. RAG 与知识库

### 6.1 mate-tech-rag

**真实能力：**

- 上传/解析/入库/检索路由存在。
- 有 RAGFlow HTTP、Milvus、Neo4j、PostgreSQL、LightRAG HTTP 客户端与三策略路由。

**缺口：**

- `vector_store.py:1` 明确为 InMemory placeholder；默认 local embedder 是 384 维 hash-based demo。
- RAGFlow/LightRAG 客户端多处捕获异常后返回空或整文档单 chunk；LightRAG 可返回 `lrag-stub-*`。
- `hybrid_v2_client` 持有 InMemory fallback；依赖失败可被伪装成“成功但无结果”，健康接口仍返回 ok。
- 上传逐 chunk 顺序写 hybrid/graph/lightrag/PG，无事务、outbox、补偿和幂等状态机；中途失败会留下不一致数据。
- 没有强制 tenant_id/knowledge_base_id 隔离；全局 client/store 可能跨租户共享索引。
- PRD 所需知识库/目录/文档版本、解析任务状态、权限、删除重建、批量操作、标签、数据源等领域能力不足。

**评级：部分实现。**

### 6.2 mate-app-kb

- 只是 upload/search/chat/stream/stats 的下游门面，不是 APP-KB PRD 的完整业务聚合。
- FastAPI async 路由中调用同步 `httpx.Client`，可能阻塞事件循环。
- 没有用户/租户 token 透传、细粒度授权、重试/熔断、生命周期关闭钩子。
- `/api/v1/app-kb` 与顶层契约 `/v1/kb` 的语义和路径需要统一。

**评级：部分实现；APP-KB PRD 大部分未覆盖。**

## 7. Agent / Copilot / 数字员工 / Workflow

### 7.1 已有能力

- 主 `graph.py` 使用 LangGraph 构建 S1–S4 入口；API 支持 chat、stream、review、state。
- 有 RAG tool、Flowable HTTP tool、JSON/PG 状态保存器和基础 guardrail。

### 7.2 缺口

1. `_PENDING_REVIEWS` 是进程内全局字典，重启/多副本丢失且不共享。
2. memory 在 PG 不可用时静默降级到 `/tmp` JSON；生产故障会造成不同实例状态分叉。
3. Flowable 客户端启动探测失败或运行调用异常时自动使用 `InMemoryFlowableTool`，会把流程引擎故障伪装成成功。
4. `scenarios/s1_s4.py` 另一套构建器仅返回 dict，注释中才有 StateGraph 伪代码；测试主要验证 dict shape，不能证明场景执行。
5. S2 worker、S3 interrupt/resume、S4 BPMN 状态一致性未见生产级并发、幂等、补偿、超时和权限控制。
6. API 没有统一 JWT/tenant dependency；thread_id 读取/删除存在跨用户访问风险。
7. 顶层 COPILOT、SUPERAI、DW、WFE PRD 的会话管理、Agent 配置/版本、技能、任务、排班、审批、产物、市场/发布等大量 API 不存在。

**评级：mate-tech-agent 部分实现；COPILOT/DW/WFE 业务后端未实现或只具底层原型。**

## 8. LLM Gateway

### 8.1 已有能力

- OpenAI、Anthropic、Qwen、Doubao provider 有真实 HTTP 非流式调用；路由按 model 映射 provider。
- 独立代码包含 quota、cache、cost、PII masking、fallback/retry、tool registry、SSE 编码器。

### 8.2 缺口

- `/chat/stream` 调用 `_mock_stream`，固定输出 `hello world`。
- `/embeddings` 返回 1536 个全零浮点，明确 TODO。
- 主 `/chat` 路径只调用 provider router；未证明 quota/cache/cost/PII/fallback/tool registry 组合进请求链。
- provider 生命周期、secret 校验、连接关闭、超时分类和上游错误映射不统一。
- 没有租户配额/计费的持久化真相源，无法满足企业级 quota/cost 审计。

**评级：部分实现；stream 与 embedding 未实现。**

## 9. Ontology

### 9.1 已有能力

- ontology/class CRUD 有 Neo4j repository；有 OWL、搜索、双写器等独立组件和测试。
- instance/relation、SPARQL、explain 路由存在。

### 9.2 缺口

- `instances/store.py:38-43` 是全局进程内 dict，不调用 `main.py` 创建的 Neo4j repository。
- `sparql/api.py:39` 明确 mock；`execute_sparql(..., neo4j_session=None)` 返回空结果。
- `DualWriter` 虽存在，但未见主 ontology/instance API 注入使用；“有组件”不等于“双写链路已完成”。
- `main.py` Neo4j 连接失败只 warning，服务健康仍 ok。
- namespace 默认值不能替代从可信 token 强制得到的 tenant；全局 store 存在跨租户风险。
- APP-ONTSTUDIO PRD 中模型版本、发布、影响分析、数据中心、质量、血缘、映射、协作等大量能力不在 13 个技术端点内。

**评级：部分实现；实例持久化和 SPARQL 未实现。**

## 10. MCP

### 10.1 已有能力

- MCP SDK server、stdio transport、HTTP bridge、tool/resource/prompt registry 存在。
- 有 kb_search 和 ontology resource，工具调用做 per-tenant/per-tool 进程内限流。

### 10.2 安全与业务缺口

- `auth.py:35-52` 仅 base64 解码 payload；`verify_jwt_token` 不验签、不校验 issuer/audience，`alg:none` 或伪造签名均可能通过。这是 **P0 安全漏洞**。
- 没有强制 exp（无 exp 只 warning）；tenant 可由伪造 claim 指定。
- list tools/resources/prompts 可匿名访问；是否允许需对照安全 PRD明确。
- rate limiter 是单进程内存，无法支持多副本一致限流。
- APP-MCPHUB PRD 的服务注册、安装/卸载、配置、凭据、审核、版本、市场、健康监控等中心能力基本不存在。
- ontology resource 的后端查询存在空结果 fallback；kb_search 依赖 RAG 的不可靠降级。

**评级：部分实现且不可安全上线。**

## 11. 消息与可观测

### 11.1 mate-tech-msg

- Kafka producer 与 Redis 幂等真实存在，partition key 可用 tenant_id。
- 但幂等 key 在 Kafka 发送前写 Redis：发送失败后重试会被误判为已发布，造成消息丢失；应采用 outbox 或至少在失败时回滚 reservation/记录状态。
- topics 是固定数组，不调用 Kafka Admin。
- 主应用未展示完整 consumer、retry topic、DLQ replay、schema registry、outbox relay 和 tenant ACL。

**评级：部分实现。**

### 11.2 mate-tech-obs

- `/metrics`、OTel 初始化、自动 instrumentation、健康聚合和静态告警规则存在。
- 健康聚合对 PostgreSQL/Redis/Kafka/Neo4j 使用 `httpx.get()` 访问非 HTTP scheme，必然无法正确探测；Milvus 端口也不是普通 HTTP 健康端点。
- 默认目标仍是旧多 SPA 容器，与当前唯一 SPA 架构不一致。
- Loki/Tempo 代码主要返回环境 endpoint，没有证明日志/trace exporter 与查询闭环。
- Dashboard 的异常/RCA/remediation 不调用 OBS，而是 IAM 内的 mock 列表。

**评级：部分实现。**

## 14. 测试与质量门禁

### 14.1 实际命令结果

| 命令 | 结果 | 解释 |
|---|---|---|
| `.venv/Scripts/python.exe -m pytest -q` | 246 passed, 24 warnings | 仅默认 packages 测试；不是全仓集成结论 |
| `.venv/Scripts/python.exe -m ruff check .` | FAIL，627 errors | 未达到 Ruff 门禁 |
| `.venv/Scripts/python.exe -m pyright` | FAIL，701 errors/1 warning | 未达到 pyright strict |
| .venv/Scripts/python.exe -m pytest tests/integration -q | FAIL：3 failed、229 passed、12 skipped、7 errors | 缺 fixture、镜像版本解析错误、路由数量不足；真实 Testcontainers 12 项跳过 |

### 14.2 测试可信度问题

1. 根 `pyproject.toml` 的 `testpaths=["packages"]`，默认不会运行 `mate-platform-backend/tests/integration/`；显式运行该目录得到 3 failed、7 errors，另有 12 个真实 Testcontainers 用例跳过。
2. 默认 pytest 没有 `--cov`，无法证明 ≥80% 覆盖率。
3. 多个所谓 integration test 只是 `assert "3.12" == "3.12"`、`assert 100 == 100`、`assert 429 == 429` 等常量自证；这类测试不触达生产代码。
4. RAG/Agent/Flowable/Neo4j/Kafka 等测试大量使用 mock/in-memory，不能证明真实基础设施兼容性。
5. 未见稳定 Pact 契约测试和 oasdiff 门禁执行证据。
6. FastAPI `on_event` 已弃用；Ruff/pyright 大量错误也暴露代码整合质量不足。

结论：测试可证明部分纯函数和内存实现行为，但**不能证明生产业务逻辑或架构集成已经完成**。

## 15. 风险分级与整改优先级

### P0：上线阻断

1. MCP JWT 不验签；立即改为复用 AuthService/JWKS 校验并强制 issuer/audience/exp。
2. IAM 管理接口允许开发 Header 注入管理员角色；生产必须彻底禁用并阻断服务直连。
3. 清理“双身份源”：Keycloak 为唯一认证/用户角色真相源，本地 IAM 仅保存平台扩展资料和策略映射。
4. 禁止关键外部依赖静默回退为成功的内存实现；生产 profile 应 fail-closed/返回明确 degraded。
5. 补齐 tenant_id 强制上下文和所有仓储查询隔离，尤其 RAG/Agent/ONT/MCP。
6. 明确 Data Track 作为 GA 硬前置；当前 `mate-tech-data` 缺失意味着 GA 条件未满足。

### P1：核心业务闭环

1. 将 Dashboard mock 替换为 Flowable、MSG、OBS、Agent、真实通知/产物查询。
2. RAG 建立 KB/Document/Ingestion 状态机、幂等、outbox/补偿和删除重建一致性。
3. Agent 将 review/state/Flowable 迁至共享持久化，禁止多副本状态分叉。
4. 完成 LLM stream 和 embedding，串联 quota/cache/cost/PII/fallback 主链。
5. ONT instances/SPARQL 接入 Neo4j，并将 dual writer 真正注入主用例。
6. 建设 APPHUB、EA、WFE、COPILOT、DW、A2A 的业务 API，而非只暴露技术服务。

### P2：工程质量与运营

1. 修复 Ruff/Pyright 到零错误；建立 CI required checks。
2. 默认 pytest 纳入 integration/contract，启用 coverage fail-under=80。
3. 用 Testcontainers 验证 PG/Redis/Kafka/Milvus；用真实 Keycloak/Flowable/Drools 做契约测试。
4. 引入 Alembic、Nacos、统一错误模型、trace/tenant middleware、secret 管理。
5. 修正 OBS 健康探测协议和唯一 SPA 目标。

## 16. 建议的验收重构

后续每个模块应采用下列七级门禁，而非“路由存在率”：

1. **PRD 门禁**：每条 FR/按钮动作映射到 use case。
2. **契约门禁**：OpenAPI path、method、schema、error code 与 PRD一致。
3. **业务门禁**：状态机、权限、幂等、并发和异常分支有实现。
4. **数据门禁**：生产仓储/外部引擎接通，不允许无声明内存替代。
5. **安全门禁**：可信 JWT、tenant、RBAC/ABAC、审计、secret 均闭环。
6. **验证门禁**：单测 + Testcontainers + Pact + E2E，覆盖率达标。
7. **运行门禁**：readyz、指标、trace、日志、回滚和故障演练通过。

## 17. 最终判断

- **是否已经实现所有后端逻辑：否。**
- **是否完成当前服务 OpenAPI 的路由骨架：大体是，但该指标范围窄且容易误导。**
- **是否达到技术架构 v3.0 的完整实现：否，主要缺失 Outbox/Saga/Drools ACL/Nacos/统一多租户与生产持久化。**
- **是否达到 v3.1 Data-Ready Baseline：否，`mate-tech-data` 及控制面未实现。**
- **是否达到全部 PRD：否，APPHUB/ARCH/WFE/COPILOT/DW/A2A/Data 等域存在大面积空白，Dashboard/部分 KB/ONT/MCP 仍是 mock 或技术原型。**
- **当前推荐阶段标识：Development Prototype / Integration Skeleton，不应标记为 Backend Complete 或 GA Ready。**
