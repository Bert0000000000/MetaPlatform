# SuperAI 能力方案（完整版 · 2026-09-16）

> 本文是给决策看的**完整方案**，用大白话写。技术细节在 `§8 附录`。
> 配套：ADR-0066（设计稿，已接受）、`REPORT-LangChain与AgentNative调研-2026-09-16.md`（开源调研）。

---

## 1. 一句话

**把 SuperAI 从"一个会聊天的助手"，做成"一个能自己组队、把活派给数字员工、把结果收回来"的指挥中枢；数字员工既能"正式入职"（登记在册、长期存在），也能"临时雇一个"（用完即走）。**

---

## 2. 目标：SuperAI 要会哪几件事

用你的原话说，是这五件：

| # | 能力 | 说人话 |
|---|---|---|
| 1 | **实例化数字员工** | 能"聘用"一个有名有姓的员工，比如"本体专员"，登记在册，下次还能用 |
| 2 | **动态加载** | 遇到没对口员工的任务，能临时配一个（现给提示词、现给权限），用完就散 |
| 3 | **统一调用** | 不管是聘来的还是临时的，SuperAI 用**同一个动作**把活派出去、把结果收回来 |
| 4 | **组队协同** | 多个员工能**互相配合**——派活、追问、取结果，不是各干各的 |
| 5 | **能力可插拔** | 员工身上挂的"技能包"（skills）、"工具"（MCP）、"数据"，能配、能换、能按需加载 |

外加一条底座：**沙箱**——员工跑代码时必须关在笼子里。

## 3. 现在到哪了

### 3.1 已经有的（不用重做）

| 有的东西 | 在哪 | 状态 |
|---|---|---|
| 数字员工名册（能建、能改、能停用） | `mate-tech-dw` | ✅ 能用 |
| 员工的能力配置（提示词 / 模型 / 工具 / 知识库） | 同上 | ✅ 能用 |
| 技能包仓库（上传 / 安装 / 公开私有） | SkillHub | ✅ 能用 |
| 工具中心（MCP，能注册能调） | MCP 中心 | ✅ 能用 |
| 网页会话（能聊天、能出证据卡片、能弹确认卡） | SuperAI 聊天页 | ✅ 能用 |
| 权限、审计、多租户隔离 | 全平台 | ✅ 很强 |

### 3.2 缺的（这是要干的活）

| # | 缺什么 | 说人话 | 严重度 |
|---|---|---|---|
| **1** | **员工"调不动"** | 名册里的员工，调度系统**不认识**。因为名册和调度器是**两套互不相通的本子** | 🔴 最严重 |
| **2** | **员工"不会干活"** | 派活出去，返回的可能是**把原话抄一遍**（假回执），不是真结果 | 🔴 最严重 |
| **3** | **没有"临时雇人"** | 只有"正式入职"，没有"临时配一个" | 🟠 |
| **4** | **没有"组队"** | 只能一个个派活，员工之间不能通信、不能互相追问 | 🟠 |
| **5** | **计划重启就丢** | 任务计划存在**内存**里，服务重启就没了 | 🟠 |
| **6** | **沙箱的信任标准错了** | 现在按"谁出品的"分安全等级；**但 AI 生成的代码本身不可信**，跟谁出的无关（详见 §6） | 🔴 安全 |

### 3.3 一句话概括现状

> **横向都齐了，纵向断在"员工不干活"。** 治理（权限/审计/多租户）和协议（MCP/A2A）比外面成熟的框架还完整；但"员工真跑一轮"和"团队协同"这两层是空的。

## 4. 三个参照物教会我们什么

我们对着三个成熟产品做了逐项比对。**每条只说最有用的 2-3 句。**

### 4.1 Codex（OpenAI 的终端编码助手）

- **它的程序化接口最干净**：命令行 `codex exec` + `--json` 输出**一行行结构化的执行事件**（谁在什么时刻调了什么工具、结果是什么），还有 Python/TS 的 SDK。**这正好是我们将来"把配置下发给 Codex 让它干活、再把结果读回来"的现成通道。**
- **它的"命令放行规则"值得学**：用一份规则文件规定"哪些命令能跑、哪些必须问、哪些禁止"，**最严的规则优先**。而且是两层分离——**"能不能跑"是一层，"要不要人批准"是另一层**。
- 它的技能包可以**声明自己依赖哪些工具**（包括 MCP 服务器）。

### 4.2 Claude Code（Anthropic 的终端编码助手）

- **它的"子员工"配置格式，和我们的设计几乎一模一样**（提示词 / 工具白名单 / 挂哪些技能 / 挂哪些 MCP / 权限模式 / 沙箱），而且**正文就是该员工自己的系统提示词，不继承主助手**。→ **我们的设计被验证了，字段表可以直接抄。**
- **两个可直接采用的默认值**：嵌套最深 **3 层**；同时最多 **20 个**并行。→ 我们现在"深度没定义、并发不设限"，这两个数字比我们拍的更靠谱。
- **技能加载是"渐进"的**：一开始只看到技能清单（名字 + 一句描述），选中了才读正文。→ 正好解决"技能一多把提示词撑爆"。

### 4.3 WorkBuddy（腾讯云的数字员工平台）

- **Agent Swarm**：一句任务拆成十几个子智能体**并行**干活，"统一框架下发、各自开工"。
- **关键一句**："每个 Agent 的指令极度简单明确，信息传递不变形。" → **下发给子员工的上下文要裁剪过**，不能把主助手的全部上下文照搬。

### 4.4 一条跨厂商的收敛信号

Codex 和 Claude Code 都读 **`.agents/skills/` 目录 + `SKILL.md`** 这套格式，而且有一个**跨工具的公共字段子集（6 个字段）**，超出就报错。

> **对我们的意义**：**我们的技能仓库如果按这个标准存，技能就能在 Codex / Claude Code / 我们平台之间搬来搬去**。这比自造一套格式值钱得多。

## 5. 方案：四层

用一个类比：**把 SuperAI 想成一个公司**。

```text
┌─────────────────────────────────────────────────────┐
│  第一层：人事档案（谁能干、能干到什么程度）           │
│    角色身份 + 技能 + 工具 + 权限范围                  │
├─────────────────────────────────────────────────────┤
│  第二层：指挥层（谁来决定怎么干）   ← SuperAI         │
│    把一句话拆成任务图，决定派给谁、并行还是串行        │
├─────────────────────────────────────────────────────┤
│  第三层：干活层（真的去干活的人）                     │
│    每个"员工实例"：自己的提示词 + 自己的工具 + 自己的线程│
├─────────────────────────────────────────────────────┤
│  第四层：通信层（公司内部的派活和汇报）               │
│    派活 / 查进度 / 取结果 / 追问 / 列清单（五个动作）  │
└─────────────────────────────────────────────────────┘
```

### 第一层：人事档案

**要做的第一件事是"合并名册"**——现在有两本互不相通的本子：

| 本子 | 记了什么 | 问题 |
|---|---|---|
| 数字员工名册 | 员工的提示词、模型、工具 | 调度系统**不认** |
| 调度角色表 | 调度系统认的角色 | **只有 4 个硬编码角色**，没有员工的参数 |

**合并成一本**，员工的全部信息（提示词 + 技能 + 工具 + 权限 + 能用哪些"运行环境"）都在里面。

### 第二层：指挥层（SuperAI）

- 收到一句话 → **拆成任务图**（哪些步骤、谁跟谁有依赖、哪些能并行、哪一步要人工确认）
- 决定：用现成的员工，还是**临时配一个**
- 把结果**汇总**给人看

### 第三层：干活层

**每个"员工实例" = 三样东西**：一段提示词 + 一篮子工具 + 一条独立的对话线程。

两种来源，**产出同一种东西**：

| 来源 | 类比 | 怎么来 |
|---|---|---|
| 正式员工 | 登记在册 | 引用名册里的 `profileId` |
| 临时员工 | 用完即走 | 当场给 `inlineProfile`（提示词 + 工具） |

**这条设计直接解决了一个死结**：我们平台的"角色种类"是**写死的 8 种**，不允许新增（这是既有硬约束）。所以"动态创建新角色"这条路走不通。但**改成"临时雇人"就绕开了**——临时员工不是新角色，只是一次任务里的一段提示词。

**引擎**：这一层我们不自己写循环了，**用成熟组件 `openai-agents`**（OpenAI 开源、MIT），它负责"调模型 → 调工具 → 拿结果 → 再调"这个循环。**但有一条纪律**：框架必须**藏在翻译器后面**，不许把它的概念漏到我们的接口上——否则将来接 Codex 会返工（详见 §7 风险）。

### 第四层：通信层

**五个动作**，对标成熟产品：

| 动作 | 干什么 |
|---|---|
| 派活 | 起一个员工任务 |
| 查进度 | 看它干到哪了 |
| 取结果 | 拿它的产出 |
| 追问 | 给它补一句话 |
| 列清单 | 看这个任务下面派出去几个人 |

配两个闸门：**嵌套深度**（防止无限套娃）和**并发数**。

## 6. 必须处理的一个安全问题

**问题**：现在的沙箱分层是**按"谁出品的"定的**——平台内置的员工给"中等"隔离，第三方的给"最强"隔离。

**为什么错了**：**AI 生成的代码，本身就是不可信的**——它是没有经过人审阅的机器输出。跟"哪个员工写的"没关系。

**证据**：**Codex 和 Claude Code 都不肯裸跑这种代码**——哪怕跑的是它自己的官方助手、在你自己电脑上，也要加操作系统级的文件/网络围栏。

**要改成**：**按"代码来源"分**——

- AI 生成的 / 子员工生成的代码 → **最强隔离**（哪怕员工是内置的）
- 人工写好、输入也校验过的代码 → 中等隔离

**还有一条配套**：现在的"会话沙箱"（一个用户一个，能活 30 分钟到 24 小时）**不能直接用来跑 AI 生成的代码**——否则**第 N 次调用的代码可以污染第 N+1 次，还能读到别人的数据**。

**正确做法**：会话沙箱当**底座**（预热好环境），**每次子员工要跑代码时，从底座"复制一份"出来跑，跑完扔掉**。

## 7. 方案分期

| 期 | 做什么 | 做完能演示什么 | 估时 |
|---|---|---|---|
| **0** | 名册合并 + 补一个缺失的"读员工名册的通道" | 员工名册和调度系统是同一本 | 1.5 周 |
| **1** | 通信层最小闭环（派活 / 查进度 / 取结果）+ 落库 + 深度闸门 | SuperAI 派活给一个员工，**拿回真结果**（不再是假回执） | 1.5 周 |
| **2** | 指挥层会规划（任务图 + 并行 + 计划落库） | 一句话 → 并行派给好几个员工 → 收齐 | 1.5 周 |
| **3** | 双向消息 + 前端卡片 | 能追问员工；界面上看到每个员工的实时状态卡片 | 1 周 |
| **4** | 人事档案完整化（临时雇人 + 权限范围 + 导入） | 临时配一个"订单分析师"，直接派活 | 1.5 周 |
| **5** | 技能按需读 | 员工身上挂 20 个技能，提示词也不爆 | 0.5 周 |
| **6** | （later）接第一个外部助手（Codex 或 Claude Code） | 把配置下发给 Codex，让它干活，收回结果 | 另立 |

**第 1 期是关键路径**——它一次解决最严重的两个问题（调不动 + 不干活）。

**每期的交付物**（按项目规矩）：先写接口契约 → 再写失败测试 → 再写代码 → 最后出验收证据。

### 风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **框架概念漏出来** | 如果图省事直接用 `openai-agents` 的概念当接口，将来接 Codex 必然返工 | 定死一条：**接口只认我们自己的概念**，框架藏在翻译器后面；用测试守住 |
| **引进了 OpenAI 的包** | `openai-agents` 依赖 OpenAI 官方客户端包 | 功能上无害（我们的网关本来就是 OpenAI 兼容协议），但这是个**治理决定**，明确记录下来 |
| **并发不设限** | 没有实测数据支撑 | **采纳 Claude Code 的默认 20**，可配 |

## 10. 附录：证据与术语对照

### 10.1 术语对照（前面用过的代号 → 人话）

| 术语 | 人话 |
|---|---|
| 能力衰减 / 权限包络 | **下级的钥匙 ⊆ 上级的钥匙**——子员工不能拿到主助手没有的权限 |
| 任务作用域子 agent | 临时员工，一次任务内有效 |
| Projection Adapter / 下放 | 把我们平台的角色配置，"翻译"成某个外部助手认识的格式 |
| RuntimeKind | 员工在**哪台机器/哪种助手**上干活（我们自己的 / Codex / Claude Code / dsh） |
| HITL | 人工确认闸门 |
| proposal | 待人工确认的提案卡片 |

### 10.2 四路调研的原始结论去哪找

| 调研 | 结论 |
|---|---|
| 开源 agent 框架六候选（langgraph / crewAI / agno / openai-agents / google-adk / pydantic-ai） | `ADR-0066 §1.4` 选型表 |
| langgraph vs 自研编排引擎 | **不换**。理由：它的"暂停恢复"会重跑节点，会把我们的"提案确认"机制搞乱；而且它的执行状态存成不可读的二进制块，审计不友好 |
| Codex 能力面 | 本文 §4.1；原始发现见会话记录 |
| Claude Code 能力面 | 本文 §4.2 |
| 沙箱机制比选 | 本文 §6；建议用 **gVisor** 做主力隔离（开源、活跃、不需要特殊硬件） |

### 10.3 明确"不引入"的清单

| 不引入 | 原因 |
|---|---|
| langchain / langgraph | 硬拖依赖 + 和我们已定的编排引擎（Temporal）冲突 |
| crewAI | 人工确认机制只在它自己的流程引擎里；核心硬拖两个向量库 |
| Google ADK | 强制用它自己的会话层 + 自带一套流程引擎 |
| AutoGen | 许可证是内容许可（非软件许可）+ 停更 5 个月 |
| agent-native | 是整套平台（会要求用 TS 重写全站） |
| Daytona（沙箱） | AGPL 许可 + 已停止维护 |
| Modal（沙箱） | 运行时是专有云 |

**保留备选**：agno、pydantic-ai（如果 `openai-agents` 实测不通，按此顺序回退）。
