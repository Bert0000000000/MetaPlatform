## 1. 版本目标与验收主线

让业务人员能够完成“理解平台 → 登录工作区 → 接入数据 → 建立对象与关系 → 校验和发布 → 从模板生成应用 → 在应用中执行经确认的业务动作 → 查看结果、审计与恢复”，让 dsh、WorkBuddy 能在明确权限内消费同一组平台能力。

以现有订单域为首条验收链路：PostgreSQL 订单表或 CSV → 订单/客户对象及关联 → 数据预检 → 发布模型 → 订单审核应用 → 人工确认动作 → 执行回执 → 数据与应用版本可追溯 → 重启后恢复 → 外部 Agent 查询同一订单并提出动作建议。

数据平台管理技术资产、连接与运行；本体平台管理业务语义、对象与动作；应用中心管理业务界面与应用发布；MCP 服务中心管理外部能力与客户端接入。保留现有八域导航，以任务向导和跨域深链串联，先解决实际操作断点。

成功指标均为**拟定目标，尚无基线测量**：

| 指标 | 1.1 目标 | 测量方式 |
|---|---|---|
| 首次使用 | 5 名首次使用者中至少 4 名，无研发代操作，在 30 分钟内完成样例数据 → 可运行应用 | 统一样例、录屏、任务计时；不把观看演示计为完成 |
| 正确理解 | 至少 4/5 人能区分业务对象、技术表、应用版本、模型版本 | 完成后提问与任务复述 |
| 失败恢复 | 断连、错列、权限不足、任务中断都有可理解提示和明确下一步 | 故障注入及恢复验收 |
| 数据可靠性 | 重试不重复生成订单；已完成批次、游标和回执重启后可恢复 | 真实 PG 测试和进程重启 |
| Agent 接入 | 两客户端各完成安装/授权/发现/查询/拒绝越权/断线恢复/撤销授权 | 客户端版本、服务版本与协议记录留档 |
| 页面性能 | 约定样本规模下关键列表操作 P95 ≤ 2 秒，官网移动端无横向溢出 | 先采集基线，再记录缓存状态、数据量与并发 |
| 服务稳定性 | 试运行 SLO 99.5%，核心路径连续 72 小时无未处理 P0 故障 | 外部探针测量业务接口；健康检查不替代业务验证 |

## 4. 数据平台：从填参数到可以信任的数据

### 2026-10-13 用户授权补齐：关系端点的子类型兼容

MP11-ONT-07 的“类型不匹配”指端点既不是声明类型、也不是其同租户合法后代。沿 ObjectType.parent_class 判断传递继承；源和目标均允许合法后代，不允许反向使用、兄弟类、无关类、跨租户、断链或循环继承。共享关系保留原 LinkType RID、方向及基数，子类适用不会复制关系定义、实例或放宽基数约束。

HTTP 和内存、PostgreSQL 写入校验一致；PostgreSQL 在原关系定义与实例事务锁内读取并锁定继承链，避免并发改父类绕过校验。实例查询沿用已有父类包含后代语义；类型 inspect 列出继承适用关系并标明声明端点。数据同步继续通过同一原生关系写入入口。

模型详情区分直接关系与继承适用关系，注明声明父类。全图保留直接定义；选择子类后可按需展开继承适用关系线，标注“继承适用”，点击仍打开原关系定义。断链不推断关系。验收覆盖植物标本→乔木标本→落叶乔木标本、多级两端继承、反向/兄弟/跨租户拒绝、重复请求、基数及真实 PostgreSQL。

用户已于本会话确认示意图：子类→父类用紫色实线及空心三角，标注“是一种”；业务关系用青色实线普通箭头并显示名称；继承适用连线默认收起，详情列出适用关系及声明父类，展开时用虚线普通箭头区分派生显示。候选预览与工作台复用同一组件。此为本平台既有 parent_class 模型的展示约定，不称为 Palantir 官方继承线标准；Palantir 官方接口概览、接口关系约束、接口实现文档说明的是接口扩展和具体关系映射，与本平台子类关系兼容规则有区别。

源码复核补充：目前“新建本体”仅写 ObjectType；LinkType/LinkInstance 已有后端接口，但关系页和模型图以浏览为主。上述三项为首次可用链路前置条件，不能等到图谱视觉优化后再补。

WebProtégé 借鉴变更、协作与权限呈现；Ontop 借鉴关系表映射语义；Jena 用作标准验证参考。当前业务 ObjectType/LinkType/ActionType 不直接等同于完整 OWL 推理语义，任何转换都要说明支持子集、丢失项与回导行为。

## 6. 应用中心：从设计器到可用应用

入口保持我的应用、模板、设计器与市场，补充“运行/编辑/发布”明确分工。应用卡片显示真实业务名、责任人、发布版本、最近修改时间、依赖状态；不把 tags 数量当模块数，也不把 version 当更新时间。

从模板创建四步：选订单审核模板 → 选择已发布业务对象与 ObjectSet → 绑定表单/表格/动作 → 预览与权限检查 → 发布并打开独立运行应用。设计器使用实际字段类型生成控件和验证，运行应用执行同一版本的 schema、权限和动作。

发布前展示检查表：数据绑定存在、引用版本有效、角色可访问、必填组件齐全、动作执行策略明确、运行页面可加载。演示内容由显式演示模式触发，正式版本为空时显示可修复的阻断状态；短链 401/403 与 404 分开处理。

| ID | 优先级 | 增量 | 依赖及验收 |
|---|---|---|---|
| MP11-APP-01 | P0 | API 元数据字段对齐 | 版本、状态、更新时间、模块数各自真实；未提供时显示未知；测试覆盖真实字段与缺失字段 |
| MP11-APP-02 | P0 | 注册/设计/发布/运行存储路径验证 | 同一应用 ID 从创建到 SQL 发布/运行可追踪；进程重启后仍存在；生产不能依赖默认内存 seed |
| MP11-APP-03 | P0 | 对象驱动模板和真实运行 | 依赖 DATA-02/ONT-03；订单模板可查看真实订单、编辑授权字段、发起确认动作并查看回执 |
| MP11-APP-04 | P0 | 发布预检与显式演示模式 | 空渲染树正式应用不自动替换成 demo；未满足依赖无法发布；错误短链不进入另一个应用 |

对标 Appsmith 的绑定与预览体验、NocoBase 的业务数据模型驱动与插件依赖呈现。NocoBase 当前授权文本、包许可证与源码头部存在多种口径，1.1 默认只做设计参考；任何源码摘取或产品嵌入须逐模块解决授权。应用中心继续基于现有 React/Semi、设计器、AppHub 与 Temporal。

## 7. dsh / WorkBuddy 与插件接入

方向一是外部 Agent 使用 MetaPlatform 工具/业务上下文，纳入 1.1。方向二是 MetaPlatform 托管并调度外部 Agent 执行任务，需要其官方调用与生命周期契约，列为后续方案；MCP 不能自动替代 Agent 运行协议。

MCP 能力面沿用现有服务，默认提供只读发现、Schema、对象查询、数据质量/血缘摘要与应用信息。写操作复用 Proposal 的预览、确认和执行链路；授权界面必须显示动作、目标、字段变更与批准期限。Agent 返回需要确认的 Proposal 深链，由已认证人完成确认。工具名、输入/输出 schema 与版本兼容是稳定契约。

当前 `ont_confirm_proposal`、`ont_execute_proposal` 等工具已经存在，不能仅凭模型侧提示词保证安全；新增客户端的工具可见性、可调用性与批准主体必须由后端校验。已有 Keycloak/API Key 能力复用，必要的 capability scope 是增量，不另建用户库。HTTP 标准 OAuth 完整发现与 PKCE 支持按客户端真实能力验收，不能把“能接受 Bearer”称为完整 MCP OAuth。

## 8. 稳定性与发布标准

| ID | 优先级 | 增量 | 验收 |
|---|---|---|---|
| MP11-REL-01 | P0 | 公共异步操作状态与错误恢复 | 连接、同步、发布、执行在成功/失败/取消均收敛；保留错误上下文和 traceId；断网重连不覆盖已编辑草稿 |
| MP11-REL-02 | P0 | 持久化、迁移和幂等完整链路 | 新库/升级库均跑订单链路；重启、重复请求、缺表、冲突和回滚有实际证据；当前历史缺表提示须在目标环境重新复核 |
| MP11-REL-03 | P0 | 业务探针和隔离故障验证 | 除 health 外执行受控只读查询；源断连、工具不可用、消费者延迟、任务中断有降级和恢复；不重置共享数据库 |
| MP11-REL-04 | P1 | 版本锁定、逐步发布与恢复说明 | 前后端/契约/迁移/插件版本成套登记；小范围试运行后扩大；回滚应用发布与数据补偿分别演练 |

完整验收场景：

1. 官网 → 登录 → 工作区 → PG/CSV 接入 → 字段映射 → 预检 → 发布 → 应用 → 人工批准 → 执行回执，重新登录与重启后仍可追踪。
2. 错密码、断网、缺权限、重复主键、无效时间列、字段删除、同步中断与重复重试，每个场景都得到可恢复结果。
3. 1.1.0 的 MCP 协议验证查询同一对象；另一个租户读不到；只读身份无法确认或执行；批准过期不能执行；相同幂等键最多一次副作用。dsh 与 WorkBuddy 真客户端复验纳入 1.1.1。
4. 空运行树/无效短链/无权应用可解释地失败；任何正式失败不能静默变成演示成功。
5. 新建测试库与从前一版本升级的测试库都通过；使用临时数据库和独立预览端口，不替换用户正在使用的服务。
