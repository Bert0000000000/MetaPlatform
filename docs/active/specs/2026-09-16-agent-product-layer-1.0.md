# Agent 产品层 1.0 —— 定义与建设计划

> 日期：2026-09-16 · 状态：**待确认**
> 底座：**langchain / langgraph**（用户 2026-09-16 拍板）
> 上游：`2026-09-16-superai-capability-plan.md`（能力面）、ADR-0066（身份与协同设计）

## 1. 定位（一句话）

**Agent 产品层 = 云端大脑 + 数字员工**：坐在 Ontology 本体上，外联 MCP/A2A，形态是**云端服务**而不是本地工具。
**1.0 只做一条完整主链**——不追求能力全覆盖，追求**端到端真跑通**。

```
        用户一句话
            ↓
   ┌────────────────────┐
   │  超级大脑 SuperAI   │  理解 → 拆任务 → 派活 → 汇总
   └────────────────────┘
            ↓ 派活
   ┌────────────────────┐
   │  数字员工（动态）    │  各自的身份 + 技能 + 工具 + 沙箱
   └────────────────────┘
            ↓ 读写
   ┌────────────────────┐
   │  Ontology 本体核心   │
   └────────────────────┘
            ↕ 外联
      MCP（工具） / A2A（其他 Agent 系统）
```

## 2. 底座：langchain / langgraph

选它的理由（按产品层标准）：图编排最强（分支/并行/嵌套）、自带持久化执行、
22 个现成中间件（摘要压缩/限流/降级/敏感信息）、生态最大（146K★ + 41.7K★）、
长期存续最稳。

**代价**：硬拖 `langchain-core`；世界观是"画图"；子 agent 的高级形态（supervisor/swarm）
在两个小卫星仓库里（各 ~1.6K★），需要自己接。

## 3. 1.0 的验收：一条主链端到端

**验收场景**：

> 用户在云端说一句话（例："把本月的异常订单找出来，逐个分析原因，给我一份汇总"）
> → 大脑拆成任务图
> → **并行派给 2 个以上数字员工**（各自有自己的提示词和工具）
> → 员工**真实执行**（调 LLM、调工具、读写本体）
> → 中间**至少一处停下来等人确认**
> → 汇总结果给人看
> → **全程在正确的租户里**（另一个租户看不到任何痕迹）

**"真实执行"是关键**：现在系统里派活出去可能返回"把原话抄一遍"的假回执，1.0 必须返回**真结果**。

## 4. 1.0 范围：每块只做最小可用形态

| # | 能力 | **1.0 做什么** | 1.0 不做什么（later） |
|---|---|---|---|
| 1 | **大脑** | langgraph 任务图：拆解 / 并行 / 一处人工确认 | 复杂图、回环、子图嵌套 |
| 2 | **数字员工** | 身份 = 提示词 + 技能清单 + 工具白名单；运行时动态构成 | 完整权限包络衰减、正式/临时员工的完整区分 |
| 3 | **Skills** | 从现有 SkillHub 读；**渐进加载**（先给清单，用到才读正文） | 技能市场、技能自带工具依赖 |
| 4 | **工具** | 接**现有 MCP 中心**，不新建 | 工具级 allow/deny 策略层 |
| 5 | **沙箱** | 员工执行代码时隔离（**先上最小可用**） | 分级（L1/L2/L3）、会话快照、per-call fork |
| 6 | **多租户** | 每个租户一个隔离的 agent 世界（会话/员工/状态） | — |
| 7 | **本体** | 员工通过**既有 Action 通道**读写本体 | 新的本体交互方式 |
| 8 | **人工确认** | 至少一处 HITL | 完整的三闸门/审批矩阵 |
| 9 | **A2A 外联** | **只留接口，不实现** | 真的联动外部 agent 系统 |
| 10 | **多运行时**（Codex/dsh） | **只留接口，不实现** | 接外部 agent 客户端 |

**一句话**：**1.0 = 一条主链 + 每块的最小形态**，不是"每块都做全套"。

## 5. 建设计划

| 步 | 内容 | 为什么这个顺序 |
|---|---|---|
| **0** | **先验证地基**：langgraph 能不能做**租户隔离**（两个租户的会话/状态互不可见） | 这是**产品层的地基**。两个框架都只在"单用户开发者工具"语境里设计过，不验证就动工有翻车风险 |
| **1** | **大脑骨架**：langgraph 图 + 任务拆解 + 并行派活 | 主链的上半段 |
| **2** | **数字员工运行时**：员工被真实跑起来（提示词 + 技能 + 工具 + 沙箱） | 主链的下半段；**解决"假回执"** |
| **3** | **打通本体**：员工能通过既有 Action 通道读写本体 | 让员工"有东西可干" |
| **4** | **人工确认**：至少一处 HITL | 平台原则（AI 只能提议，人确认才落库） |
| **5** | **前端**：能看到任务图、员工状态、结果 | 可演示 |
| **6** | **Skills 渐进加载** | 员工一多，提示词会爆 |

## 6. 地基验证（第 0 步）要验什么

| # | 要验证 | 为什么 |
|---|---|---|
| 1 | langgraph 的**会话/状态**能不能加租户维度 | 它按 `thread_id` 存状态，是单用户视角 |
| 2 | 它的 **checkpointer 表结构**能不能嵌进我们的库、能不能按租户分区 | 决定要不要自建存储 |
| 3 | 它能不能**跑在我们的服务里**（而不是当独立服务部署） | 形态是"产品层"，不是"再部署一个系统" |
| 4 | 它的**工具接口**能不能接我们的 MCP 中心 | 工具面是我们既有的 |
| 5 | 不用它的 `interrupt()` 时，**暂停恢复**我们能不能自己做 | 保护既有的"提案确认"机制 |

**不通过就有翻车风险**——这一步只花 2–3 天，值得。
