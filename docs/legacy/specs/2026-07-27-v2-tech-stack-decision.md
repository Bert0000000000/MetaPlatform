## 1. v1.2 复盘（为什么废止）

### 1.1 v1.2 原始决策

```
"后端统一为 Java 25 + Spring AI Alibaba（SAA），禁止新增 Python 业务后端"
—— 见 agent.md v1.2 决策记录（2026-07-21）
```

### 1.2 v1.2 当时的动机

| # | 动机 | v1.2 设计意图 |
|---|---|---|
| M1 | 运维少一套栈 | 避免 K8s 上跑多语言 Runtime |
| M2 | 团队技能统一 | 避免需要 Python 工程师 |
| M3 | 性能统一管控 | 避免 GIL / 内存模型差异 |
| M4 | 架构简洁美观 | 单一栈的工程美感 |

### 1.3 现状（2026-07-27）

| 动机 | 现状 | 评估 |
|---|---|---|
| M1 | DeerFlow 已是 Python 运行时，**实际已破例** | ⚠️ v1.2 已被现实打破 |
| M2 | DeerFlow 集成让团队已具备 Python 能力 | ⚠️ 不再是门槛 |
| M3 | RAGFlow 等 Python 工具性能已证明可用 | 🟡 不再是关键 |
| M4 | 已有多栈（DeerFlow、可能的 RAGFlow/GraphRAG） | ⚠️ 已被现实打破 |

### 1.4 复盘结论

**v1.2 的核心动机（M1 "运维少一套栈"）在新的协作模式下（AI 作为技术专家）已不再成立**：
- AI 可以在多语言栈之间提供翻译、调试、文档支持
- 团队配置已不再由单一工程师决定
- 运维复杂度的核心是**可观测性**，不是语言

## 2. v2 决策核心

### 2.1 新公理

> **AI 作为技术专家**是新的协作维度。
> 架构决策**不再仅以"个人能力上限"为约束**，而是以"团队 + AI + 法务"三重判断为约束。

### 2.2 v2 决策原则（7 条铁律）

| # | 原则 | 说明 |
|---|---|---|
| **P1** | **主力栈优先** | 新项目默认 Java 21 + SAA 1.1.2，享受 BOM 统一、生态成熟的红利 |
| **P2** | **AI 子域例外** | Agent Runtime、复杂 RAG、OCR/版面等**AI 子域**允许 Python，**不**需要"破例"申请 |
| **P3** | **核心业务后端禁 Python** | 交易、订单、权限、计费等**核心业务后端**仍**必须** Java，**不**允许 Python |
| **P4** | **法务合规是硬约束** | 任何新引入的开源组件（不**分**语言）**必须**过 LEGAL_CLEARANCE |
| **P5** | **可观测性高于语言统一** | 跨语言栈**必须**统一接入 TECH-OBS，统一告警面板 |
| **P6** | **AI 协作是新能力维度** | 团队需**主动**与 AI 协作（review、调试、文档、跨语言翻译），**不**是"AI 替我做" |
| **P7** | **季度复盘 + 决策可逆** | 每季度复盘多语言栈实际成本；如发现代价远大于收益，**可**回退到 v1.3（仅放开 AI 子域） |

### 2.3 决策矩阵

| 场景 | 语言 | 决策依据 |
|---|---|---|
| 业务核心后端（订单、交易、权限、计费） | **Java 必须** | P3 硬约束 |
| 通用业务服务（CRUD、编排、API 网关） | Java 优先 | P1 主力栈 |
| Agent Runtime（编排/沙箱） | Python 允许 | P2 AI 子域例外（如 DeerFlow） |
| 复杂 RAG（版面分析、OCR、社区检测） | Python 允许 | P2 AI 子域例外（如 RAGFlow/GraphRAG） |
| 特定工具（PDF 解析、图像处理、ML 推理） | Python/Go/Rust 允许 | P2 工具特例 |
| 前端 | TypeScript（不变） | 不在本决策范围 |
| 数据 ETL / 数据科学 | Python 优先 | 历史原因 + 生态成熟 |

### 2.4 与 v1.2 的关系

```
v1.2（已废止）
   │
   ├── 完全禁止 Python 业务后端
   │
   ▼
v2（当前）
   │
   ├── 主力 Java + SAA（不变）
   ├── AI 子域允许 Python（新增）
   ├── 法务 + 可观测性硬约束（新增）
   └── 季度复盘（新增）
```

## 3. v2 决策的实施规则

### 3.1 新组件引入流程

```
新组件 / 新服务引入申请
        │
        ▼
   ┌─────────────┐
   │ 类别判定    │  核心业务? →  Java 必须
   │             │  AI 子域?  →  Python 允许
   │             │  通用服务? →  Java 优先
   └──────┬──────┘
          │
          ▼
   ┌─────────────┐
   │ 法务审查    │  协议合规 / 商业风险
   │ LEGAL_CLEAR │
   └──────┬──────┘
          │ 通过
          ▼
   ┌─────────────┐
   │ 架构评审    │  运维成本 / 监控接入 / 团队能力
   └──────┬──────┘
          │ 通过
          ▼
   ┌─────────────┐
   │ Pilot 部署  │  灰度 / 验证
   └──────┬──────┘
          │
          ▼
       生产
```

### 3.2 跨语言服务接入要求

不论 Java 还是 Python 服务，**必须**满足：

| 要求 | 说明 |
|---|---|
| **统一 LLM 调用** | 走 `TECH-LLMGW`（不直连模型 API） |
| **统一身份认证** | 走 `TECH-IAM`（OAuth2 / JWT） |
| **统一事件流** | 走 `TECH-MSG`（Kafka） |
| **统一可观测性** | 接入 `TECH-OBS`（OpenTelemetry） |
| **统一配置** | 走 `Nacos 3.0+` |
| **统一服务发现** | 走 `Nacos 3.0+` |

### 3.3 已有 Python 服务的处理

| 服务 | 当前状态 | v2 下处理 |
|---|---|---|
| DeerFlow | 已是 Python 运行时 | ✅ 合法化（视为 AI 子域例外） |
| RAGFlow（计划引入） | 待法务审查 | 待 LEGAL_CLEARANCE 签字后合法 |
| GraphRAG（计划引入） | 待法务审查 | 待 LEGAL_CLEARANCE 签字后合法 |

## 4. 决策可逆性（v2 → v1.3 路径）

如果 v2 在季度复盘中发现：
- 跨语言运维成本远超预期
- AI 协作未能达到承诺效果
- 核心业务被 Python 渗入

**回退路径**：
- v1.3 = "v1.2 + 仅放开 DeerFlow 例外"（仅 Agent Runtime 允许 Python）
- 决策权：架构组 + 项目 Owner
- 触发条件：连续 2 个季度复盘结论为"代驾 > 收益"
