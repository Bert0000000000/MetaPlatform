# 页面级 AI 助手侧栏设计

**日期：** 2026-07-28  
**状态：** 已经用户确认，待实现计划  
**范围：** `metaplatform-frontend/apps/portal` 中当前带有“AI 助手”入口的页面

## 1. 背景与目标

Mate Platform 的业务页面已展示“AI 助手”按钮，但当前按钮没有统一的聊天交互。不同页面或模块后续将绑定不同的数字员工，因此 AI 对话不能由全局共享 Session 承载。

本次目标是：点击页面内的“AI 助手”按钮后，使当前页面主内容收缩，并在页面右侧新增固定约 400px 的完整聊天区域。聊天区域由通用展示组件实现，但数字员工配置、开合状态、聊天消息和 Session 均由各页面独立管理。

本阶段只实现完整聊天界面、开合交互和模拟回复，不连接真实 SuperAI 或数字员工接口。

## 2. 设计原则

1. **页面级隔离：** 每个页面拥有独立数字员工、`sessionId`、消息和推荐问题，不使用全局聊天 Store。
2. **组件复用：** 聊天界面和基础交互由通用组件复用，业务状态仍由页面持有。
3. **非覆盖布局：** AI 区域属于页面正常布局，不使用 Drawer、Modal 或悬浮遮罩。
4. **渐进接入：** 组件预留真实接口所需字段，后续各页面可分别连接对应数字员工。
5. **保持现状：** 不修改现有 `/superai` 独立页面，也不改变左侧主导航和页面已有详情 Drawer。

## 3. 方案选择

### 3.1 已选择：页面独立状态 + 通用聊天组件

每个页面自行管理：

- AI 区域开合状态；
- 当前数字员工配置；
- 页面级 `sessionId`；
- 当前消息列表；
- 欢迎语和推荐问题；
- 模拟发送与回复逻辑。

通用组件只接收数据和回调，不负责跨页面状态管理。

### 3.2 未选择：全局 AI 容器

全局容器虽然能减少页面布局代码，但容易把不同模块的数字员工与 Session 绑定到同一状态源，不符合页面独立对话的业务要求。

### 3.3 未选择：嵌入 `/superai`

现有 `/superai` 是完整页面形态，直接嵌入会产生重复导航和不必要的页面耦合，也无法自然承载各模块独立的数字员工上下文。

## 4. 接入页面

本阶段接入当前已显示“AI 助手”按钮的 6 个 Portal 页面：

1. 业务架构；
2. 应用列表；
3. Ontology 建模；
4. Ontology 数据中心；
5. 知识库；
6. MCP 工具注册。

每个页面配置独立的数字员工名称、职责描述、欢迎语和 2～4 个推荐问题。

## 5. 布局设计

### 5.1 页面结构

接入页面的主体改为横向 Flex 布局：

- 原页面内容：`flex: 1; min-width: 0`；
- AI 区域：桌面宽度 400px，较窄桌面窗口允许收缩到 380px；
- 左侧主导航保持原宽度和位置；
- AI 区域打开时，原页面主内容同步收缩；
- AI 区域关闭后从页面布局中移除，主内容恢复完整宽度。

### 5.2 动效

- 开合使用约 200ms 的宽度、位移和透明度过渡；
- 动效不阻塞输入或页面操作；
- 遵循 `prefers-reduced-motion`，用户减少动效时禁用非必要过渡。

### 5.3 滚动

- 原页面继续使用现有滚动容器；
- AI 消息区独立垂直滚动；
- AI 顶部栏和输入区固定在面板内部；
- AI 区域不得导致整个浏览器页面出现额外横向滚动。

## 6. 通用组件设计

### 6.1 `AIAssistantPanel`

组件负责聊天区域显示和通用交互，建议接口如下：

```ts
interface AIAssistantPanelProps {
  employeeId: string;
  employeeName: string;
  employeeAvatar?: ReactNode;
  employeeDescription: string;
  moduleLabel: string;
  sessionId: string;
  messages: AssistantMessage[];
  suggestions: string[];
  isThinking?: boolean;
  onSend: (content: string) => void;
  onClear: () => void;
  onClose: () => void;
}
```

### 6.2 消息模型

```ts
interface AssistantMessage {
  id: string;
  role: 'user' | 'assistant';
  content: string;
  createdAt: string;
}
```

### 6.3 页面级 Hook

可提供 `usePageAssistant` 复用页面内的基础消息状态与模拟回复逻辑。该 Hook 每次调用都创建独立状态，不使用 Context、全局 Store 或跨页面单例。

建议返回：

- `isOpen`；
- `sessionId`；
- `messages`；
- `isThinking`；
- `toggle` / `open` / `close`；
- `sendMessage`；
- `clearSession`。

## 7. 聊天界面

### 7.1 顶部栏

包含：

- 数字员工头像或模块图标；
- 数字员工名称；
- 在线状态；
- 当前模块标签；
- 清空会话按钮；
- 关闭按钮。

### 7.2 消息区

初始状态显示：

- 页面专属欢迎语；
- 数字员工职责说明；
- 2～4 个页面专属推荐问题。

进入对话后显示：

- 用户和 AI 消息气泡；
- 消息时间；
- AI “正在思考”状态；
- 新消息出现后自动滚动到底部。

点击推荐问题等同于发送对应文本。

### 7.3 输入区

- 支持多行文本；
- `Enter` 发送；
- `Shift + Enter` 换行；
- 空白内容不可发送；
- 模拟回复期间允许查看消息，但避免重复触发同一发送动作；
- 发送按钮具有禁用、加载和可访问名称。

## 8. 开合与 Session 行为

1. 点击页面内“AI 助手”按钮切换 AI 区域开合状态。
2. AI 区域打开时按钮显示激活状态。
3. 点击面板关闭按钮后，页面恢复完整宽度。
4. 关闭后再次打开同一页面，保留当前组件实例内的消息。
5. 点击“清空会话”后清除消息并生成新的 `sessionId`。
6. 不同页面的数字员工、消息和 `sessionId` 相互独立。
7. 本阶段页面离开并重新进入后重新创建本地 Session；服务端历史恢复留待真实接口阶段实现。

## 9. 模拟回复

本阶段 `onSend` 使用短暂延迟模拟 AI 思考，并返回与当前模块相关的模拟回复。该回复仅用于验证完整聊天体验，不模拟工具调用、流式输出或复杂业务结果。

每个页面可以提供自己的回复生成函数或配置化回复前缀，以体现数字员工差异。

## 10. 可访问性与主题

- 使用现有 CSS 变量适配深色和浅色主题；
- 所有图标按钮提供 `title` 或 `aria-label`；
- 输入区可由键盘完成发送、换行和焦点操作；
- 激活状态不只依赖颜色表达；
- 文本和边框对比度延续现有 Portal 视觉规范。

## 11. 非目标

本阶段不包含：

- 真实 SuperAI 或数字员工 API；
- 服务端 Session 持久化和历史恢复；
- 流式输出；
- Markdown 高级渲染；
- 文件上传；
- 语音输入；
- 工具调用过程展示；
- 跨页面共享聊天记录；
- 修改现有 `/superai` 独立页面。

## 12. 验收标准

1. 点击任一接入页面的“AI 助手”按钮，右侧出现约 400px 的聊天区域。
2. 原页面同步收缩，AI 区域不覆盖原内容。
3. 再次点击按钮或点击面板关闭按钮，页面恢复原宽度。
4. 用户可以输入消息，并通过发送按钮或 `Enter` 发送。
5. `Shift + Enter` 可以换行。
6. AI 展示短暂“正在思考”状态并返回模块相关的模拟回复。
7. 点击推荐问题可以直接发起消息。
8. 关闭再打开同一页面时保留消息。
9. 清空会话后消息被清除，并生成新的页面级 `sessionId`。
10. 不同页面使用不同数字员工配置，消息和 Session 不共享。
11. 现有页面滚动、操作按钮和详情 Drawer 不受影响。
12. TypeScript 类型检查、前端构建以及新增的关键交互测试通过。

## 13. 测试建议

- Hook 单元测试：发送消息、模拟回复、清空 Session、页面实例隔离；
- 组件测试：推荐问题、Enter/Shift+Enter、关闭和清空操作；
- 页面集成测试：打开后布局收缩、关闭后恢复、按钮激活状态；
- Playwright 冒烟测试：至少覆盖业务架构页面和另一个不同模块页面，证明 Session 独立。
