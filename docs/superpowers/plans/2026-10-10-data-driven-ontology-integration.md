# 数据逆向建模接入 MetaPlatform 实施计划

> 日期：2026-10-10（Asia/Shanghai）。状态：第一期已实施，独立本地预览与工程验收；业务语义待用户确认。后续阶段仍为建议，未实施。
> 执行方式：按已确认阶段顺序实施；使用 executing-plans 跟踪任务及检查点。

**Goal:** 将 Excel 数据画像、业务语义推荐和人工审查接入本体工作室，逐步生成可由平台校验、发布及执行的业务模型。

**Architecture:** 数据接入与画像产生事实证据，AI 生成独立的候选建设方案，确定性转换器把确认内容送入平台原生治理流程。正式模型、实例和执行记录以平台为单源；生成任务和未确认建议保留为辅助记录，不构成另一套正式本体。

**Tech Stack:** 现有 Python 3.12、FastAPI、Pydantic、PostgreSQL、React/TypeScript、Node 22、pytest、Playwright；Excel 解析优先复用 openpyxl，新增依赖须登记到后端工作区锁文件。

## 1. 基线、范围与选择

- 主分支审阅基线：`816684e7`；参考功能分支：`codex/ontology-demo-flow`，末提交 `34f08c31`。实施前刷新引用并重新记录 HEAD。
- 规范单源：AGENTS.md、ADR-0080（草稿/版本）、ADR-0082（迁移）、ADR-0064（Action edits）、ADR-0063（函数来源）、ont.yaml、Builder V2 设计。
- 方案 A：整体合并旧工作台。短期页面复用最多，但保留两套发布、存储和身份机制；不推荐。
- 方案 B：迁入推荐、画像、校验能力，接入平台原生治理与数据链。需要适配，但能持续演进；推荐。
- 方案 C：独立工具仅导出文件。边界清晰，但审核、复用已有概念和数据同步不能形成平台内闭环；作为兼容出口。
- 首期输入是 Excel 和用户填写的业务说明/业务问题；业务文档自动抽取、任意数据库连接、ERP 写回不作为首期依赖。
- 首期完整交付对象、属性、关系、数据映射与原生发布；第二期扩展接口、公理、约束及派生指标；第三期扩展声明式动作与函数。
- 不以实体和属性数量为成功标准。以业务问题支撑程度、身份正确性、追溯、重复导入和平台治理一致性验收。

## 2. 全局约束

- 保留已有分支、未提交文件、现有服务和业务数据。功能开发使用新的 `codex/` 分支及隔离资源，不直接在 main 上开发。
- 验证数据库、端口、租户和 Compose 项目须独立；不在当前演示环境跑写入测试。
- AI 只生成建议，不直接修改生效模型、实例或触发业务动作。现有模型变更通过原生预检与发布门禁。
- 数据画像中的标题、内容和文档文本作为不可信数据；模型供应商沿用平台受控配置，用户输入不得覆盖任意请求地址。
- 候选内容记录来源、证据、假设、待确认项及验证结果；模型自报置信度不能替代验证。
- “当前样本满足”与“业务长期约束成立”分开记录；少量样本唯一不能自动发布为业务唯一键。
- 数据源版本、候选修订号、正式模型版本、实例同步批次四者分开，建立关联与追溯。
- 修改输入或候选语义后，关联审核和报告失效；服务端检查 revision、checksum 和执行幂等键。
- 不扩大平台已有回滚含义：模型回滚不等于恢复数据或补偿外部操作。
- 提交顺序：docs/ADR → contract → failing tests → feature → infrastructure → deploy → acceptance evidence。
- 任何不满足当前执行能力的建议可保存并展示缺口，但不得标为可执行。

## 3. 产品入口与输出

在本体工作室“业务模型”组内新增“从数据建模”，路由建议 `/ontology/model/from-data`。本体概览和对象类型列表提供入口。生成完成后跳转既有对象详情、映射、发布、对象探索及动作管理页面。

2026-10-10 用户补充：逆向建模保持独立可选辅助入口，不替代或强制接管正向本体主链路。原有手工建模默认入口保留，独立候选经人工确认发布才进入正式本体。第一期实际落地范围与验证见 [验收记录](../../acceptance/2026-10-10-data-modeling-phase1.md)。

用户流程：选择数据 → 确认画像与业务问题 → 推荐并匹配已有概念 → 审核模型/映射/规则 → 原生预检与发布 → 数据导入 → 对象查询和业务验收。

页面分为数据、模型、约束、行为及校验与发布；后续阶段未交付的面板不开放。候选图清晰区分概念图与实例预览。

建议新增内部 `ModelingPlan` 契约：

| 组成 | 用途 |
| --- | --- |
| source_refs / source_revision | 输入文件与画像版本，不把完整文件发送给模型 |
| business_questions / assumptions | 用户目标、已确认规则、缺失数据和假设 |
| object_types / properties / link_types | 候选结构；每项包含 new/reuse/extend 决策与目标 RID |
| mappings / identity_policies | 字段绑定、复合身份、合并规则、来源行追溯 |
| interfaces / axioms / constraints | 第二期候选契约及其真实校验通道 |
| derived_properties / action_types / function_specs | 按后续阶段逐步开放 |
| evidence / decisions / validation / execution_support | 证据、人工决策、检查结果和支持状态 |

`execution_support` 区分 supported、unsupported、needs_implementation；人工确认和测试通过另设字段，避免混淆“已审核”和“能执行”。关系的业务定义与数据关联规则分开建模。

## 5. 第一期：数据到原生本体闭环

### T1：冻结接入设计与验收样本

- [ ] 编写候选契约、生命周期和发布协调 ADR；将本计划中的建议落实为明确决策并同步文档索引。
- [ ] 固定两套独立样本：跨表重复物料/库存/BOM/工单，以及非齐套领域样本；覆盖一表多类、多表同类和复合身份。
- [ ] 每套由业务人员确认概念、粒度、身份和至少 5 个问题；至少包含 1 个因缺数据无法回答的问题。
- [ ] 登记基线测试、独立资源及需受影响回归的清单。

验收：有明确期望及反例；目标不是复现旧图谱数量。

### T2：Excel 来源、画像和任务持久化

- [ ] 迁移有界解析、类型画像、空值/重复统计、关联线索及来源行引用；保存不可变输入快照和画像版本。
- [ ] 通过 PostgreSQL 保存候选修订与生成/审查任务状态；按租户和用户授权访问，原始文件按既有存储约定保存并登记存储策略。
- [ ] 重启后未完成任务明确标记中断，重试不能覆盖更新的修订；任务错误不替换已有候选。
- [ ] 验证异常工作簿、容量限制、公式处理、跨租户拒绝、并发保存、重启恢复及来源追溯。

验收：真实 Excel 可导入、复查、重新打开；画像和任务不依赖 Neo4j KitModelSource。

### T3：面向业务与已有模型的推荐

- [ ] 将业务问题、用户规则、画像及授权范围内已有类型/共享属性/关系放入推荐上下文。
- [ ] 按业务实体先形成全局概念清单，再分批补属性和映射，最后统一去重；移除大工作簿分组“每表最多一个类”的限制。
- [ ] 对已有概念输出复用、扩展或新建建议及依据；相似度不能自动决定合并。
- [ ] 保留复合键、冲突检测和复合等值关联能力；记录类粒度、时间范围、单位和关系含义，缺依据时保持待确认。
- [ ] 验证跨组同一概念、多表填充同类、一表多类、错误标识、重复概念、模型截断和提示注入。

验收：候选始终可编辑，未审核时不写正式模型；数据匹配率不冒充语义正确率。

### T4：候选审核和确定性验证

- [ ] 将旧工作台的编辑、冲突/空值检查、证据定位和语义审查迁入新页面。
- [ ] 预览模型定义、字段绑定、身份合并及关系样本；明确预览取样范围。
- [ ] 业务或配置修改使相关确认和报告过期，服务端重新校验，不能仅在前端禁用按钮。
- [ ] 验证不合法引用、属性冲突、遗漏映射、关系数量限制、人工修订优先级和报告失效。

验收：每个阻断项可定位到模型或源数据；AI 审查不修改候选、不替代确定性检查。

### T5：平台草稿和发布协调

- [ ] 稳定类型家族和属性身份；输入文件、样本范围及生成批次不进入正式业务类型身份。
- [ ] 对象候选转换为平台 WIP；复用 checksum、破坏性确认、版本与影响预检。
- [ ] 接口、关系等资源的草稿支持逐项盘点；首期关系候选保留于建设方案直至确认，不伪装已有统一草稿机制。
- [ ] 发布协调按依赖先类型后关系，持久记录每项结果、基线和幂等键；首期明确采用可续传分步发布，不承诺跨所有资源原子事务。
- [ ] 失败时展示已发布、待发布及冲突资源，禁止静默覆盖或假报整体完成；不以自动删除已发布资源进行补偿。
- [ ] 验证过期候选、并发发布、已有类型复用、破坏性变更拒绝、部分失败及重试。

验收：原生类型页、版本页能读取结果；重复执行不增加重复业务类型。

### T6：数据映射、实例落地与首期验收

- [ ] Excel 先生成有来源快照的 PostgreSQL 暂存数据；确认后的实体映射形成稳定业务行，绑定平台 pg_table 数据源。
- [ ] 按业务主键确定稳定 ID；无业务主键使用来源记录身份并明确不能保证跨文件实体对齐。复合键采用无歧义规范化表示。
- [ ] 复用 backing datasource 的 field_mapping、物化、来源优先级和人工覆盖机制；关系实例由确认的关联规则确定性生成。
- [ ] 显式区分全量快照和追加批次；首期缺行默认保留，不自动删除。关联、修订及同步冲突写入批次报告。
- [ ] 验证同文件重导、改值重导、跨文件同身份、复合身份、关系稳定性、人工覆盖、租户隔离和来源追溯。
- [ ] 实际浏览器完成导入→推荐→审核→发布→同步→对象查询；在两套样本上核对业务问题。

首期退出条件：原生对象探索能读到结果，数据与模型各有可追溯版本；缺失问题诚实报告；重复导入不重复建模；旧工作台正式发布存储不成为新能力的运行依赖。

## 6. 第二期：接口、公理、约束和派生指标

### T7：能力注册表与共享接口

- [ ] 建立按执行通道登记的能力表，包含输入契约、验证器、发布适配和支持状态；以后生成仅引用已登记能力。
- [ ] 根据业务能力与已有接口推荐共享属性 RID、接口实现和必需关系；字段名称相同不构成自动抽象依据。
- [ ] 核对 required_links 和 polymorphic_action_constraints 的实际执行边界；未实现约束只能报告缺口。
- [ ] 验证缺共享属性、缺关系、错误接口实现和多态查询，并纳入依赖发布协调。

### T8：公理与数据约束

- [ ] 优先生成唯一键、子类、不相交及平台实际支持的 SHACL 约束；为每条规则附来源、适用范围、人工确认和反例。
- [ ] 原生 Axiom 校验目前执行 disjoint、has_key、subclass；其他 kind 按实际推理路径登记，skipped 不计作规则验证通过。
- [ ] 定义 SHACL 约束的持久保存、版本绑定及调用入口；不能只调用临时校验后声称平台已长期执行。
- [ ] 将业务长期约束与样本统计分开；全量唯一性校验基于来源记录，不能只检查已去重的实例。
- [ ] 对每条已支持规则用违反规则的数据验证能实际检出；记录 checked/skipped 和错误定位。

### T9：派生指标

- [ ] 开放现有 count/sum/avg 派生属性，声明遍历关系、聚合字段、粒度、单位及空值处理。
- [ ] 复杂齐套公式、时间窗口和替代料逻辑作为函数需求，不伪装成简单求和。
- [ ] 验证小样本人工计算结果、重复关联、防止计量单位混算及授权数据范围。

第二期退出条件：至少一个共享接口能多态查询；确认的约束可用反例检出；至少一个指标与人工计算一致；未执行公理明确展示。

## 7. 第三期：声明式动作和函数

### T10：从业务说明生成动作候选

- [ ] 输入增加用户确认的流程、角色、前置状态、参数及副作用说明；不从静态表格猜测业务授权。
- [ ] 优先支持 set_property、create_object、add_link 等现有声明式算子；删除类动作作为单独的显式能力开关。
- [ ] 动作条件只输出现有运行路径能执行的表达式；结构化规则类存在不等于 API/执行器已经完整接线。
- [ ] 动作定义审核与动作实例执行确认分开；调用既有 proposal/confirm/execute、权限及审计流程。
- [ ] 验证未确认不能执行、前置条件拒绝、重复执行、越权和事务失败不部分落库。

### T11：函数复用和受控实现

- [ ] 先检索可用函数；生成输入输出签名、规则口径、测试样例和依赖需求，人工决定复用或新增。
- [ ] 新函数先提交受审源码和业务反例测试，再绑定不可移动 Git SHA source_ref；RID 或签名存在不代表源码可执行。
- [ ] 校验语言和解析器/执行器匹配；配置实际 FunctionExecutor，生产路径沿用现有隔离要求。
- [ ] 计算函数与写入分开，写入经现有 Action 编辑集和事务处理；外部系统调用单独建设连接器和副作用策略。
- [ ] 验证引用无法解析、输入不全、超时、执行失败、业务反例及执行证据，才能标记已验证可执行。

第三期退出条件：至少一个真实声明式动作完成确认/执行/审计；至少一个有真实源码和测试证据的函数被调用；业务副作用范围明确。

## 8. 测试与交付

- 每项先添加能揭示业务失败的测试，再实现。纯文档变更只检查链接与一致性，不写镜像测试。
- 后端用 pytest 验证纯逻辑；持久化、版本、同步、租户和 Action 原子性使用独立 PostgreSQL 的实际集成测试。
- 前端运行 `pnpm --filter @mate/web typecheck` 与 `pnpm --filter @mate/web build`，新增 Playwright 端到端用例使用独立服务。
- 必需数据库回归按 AGENTS.md 的 `scripts/ci/verify_ont_postgres.py` 执行；受影响版本、迁移、同步及关系并发组不能以环境 skip 记作通过。
- AI 稳定性测试使用受控响应测试结构、权限与错误处理；另用真实供应商和固定样本完成业务验收，两类证据分别记录。
- 正确率以人工标注模型和业务问题为基准；登记概念重复、错误合并、错误关系、遗漏和缺口识别，不只看测试数量。
- 每期独立 PR，第一期 T1–T6 可按任务拆 PR；第二、三期分别编写细化规格后执行。本建议稿不授权发布、合并或部署。

## 9. 预估与推进建议

按一名熟悉仓库的开发者估算，另需业务人员参与语义和样本确认：第一期约 10–15 个工作日，第二期约 6–10 个工作日，第三期约 8–15 个工作日。合计约 5–8 个工作周；模型效果、复杂函数和环境准备会影响工期，该范围不是交付承诺。

推荐先实施 T1–T6。首期实际验收后，按业务价值选择接口/约束及动作试点，再细化下一期任务；不把完整平台基元生成作为第一期上线条件。
